# Cityplanner

## Миссия

3D-градостроитель в духе Cities: Skylines 1: свободные дороги на кривых Безье, зонирование
R/C/I/O, сети воды и электричества, городские сервисы, общественный транспорт, районы с
политиками, индустриальные цепочки и парковые зоны. Карта открывается тайлами. Ближе порога
зума видно пешеходов и машины, и пробки возникают из поведения агентов, а не из формулы.
Чем больше население, тем больше поездок и требований к городу.

Как собрать, запустить и играть: [`docs/PLAYING.md`](docs/PLAYING.md). Сетап на новой машине: [`docs/SETUP.md`](docs/SETUP.md).

## Стек и ключевые решения

| Область | Решение |
|---|---|
| Движок | Rust + Bevy **0.20.0** (закреплена `=0.20.0` в `[workspace.dependencies]` корневого `Cargo.toml`; смена версии — отдельная задача). Тулчейн Rust 1.99.0 (`rust-toolchain.toml`) |
| Платформы | Основная — десктоп (macOS, Windows, Linux). `wasm32` собирается в CI как демо с урезанным лимитом агентов |
| Масштаб | Карта 5×5 тайлов по 2×2 км, население 100k+. Пул агентов: ~16k машин, ~65k граждан-юнитов |
| Симуляция | Детерминированная и headless: sim-крейты на `bevy_ecs`, фиксированный тик, сидируемый RNG. Ввод игрока доходит до симуляции только командами. Рендер только читает состояние |
| Дороги | Сегменты Безье между узлами, автогеометрия перекрёстков, уклоны, эстакады и мосты (тоннели — M3). Зоны — ячейки 8×8 м вдоль дороги, глубиной до 4 |
| Трафик | Лейновый агентный: A* по графу полос с учётом загрузки, следование за лидером. На перекрёстках приоритеты и светофоры. Застрявшие машины исчезают |
| Жители | Записи граждан и домохозяйств с распорядком дня. Агент из пула выдаётся только на время поездки |
| Экономика | Спрос RCIO. Уровни зданий: 1–5 жилые, 1–3 остальные. Налоги и содержание, вехи населения, покупка тайлов |
| Карта | Рельеф из PNG-heightmap. Вода статичная (уровень моря и реки) |
| Сервисы | Трубы, ЛЭП и ёмкость сетей. Покрытие считается по расстоянию по дорогам. Сервисные машины физически ездят по дорогам |
| UI | `bevy_egui` поверх слоя команд. Стилизованный `bevy_ui` — позже |
| Контент | Здания, дороги и транспорт описаны данными в RON (`assets/content/`). Сейвы — версионированные бинарные снимки, они же тестовые фикстуры |
| Ассеты | Здания процедурные (low-poly). Машины, люди и деревья — из CC0-паков (Kenney, Quaternius). Лицензия каждого импортированного пака записывается в `assets/LICENSES.md` |
| Производительность | 60 FPS при 100k жителей на Apple M1 или GTX 1660, скорость симуляции ×3. Headless-бенч на эталонном сейве гоняется в CI |

Вне рамок до отдельного решения: звук, локализация (UI на английском), моддинг-API,
катастрофы, мультиплеер, дистрибуция, динамическая вода и терраформинг.

## Модель команды

Каждая роль — отдельная агентная сессия в своём git worktree. Брифы ролей лежат в
`agents/roles/*.md` и самодостаточны: в каждом есть всё, что нужно роли для работы с нуля.

Команда делится на два контура, и никто не работает в обоих.

**Дизайн-контур (Architect).** Идея фичи сначала записывается в `IDEAS-BACKLOG.md`.
Дальше Architect решает, что ей нужно:
- проход Researcher, если механику надо изучить (как это устроено в CS1, какие алгоритмы
  подходят);
- прогон Balance Analyst, если меняется баланс.

Контур заканчивается, когда Architect раскладывает утверждённый дизайн на задачи в
`tasks.jsonl`.

**Контур поставки (Tech Lead).** Всё, что ниже декомпозиции:
- Software Engineer (2–3 постоянных слота);
- Technical Artist;
- Tester;
- DevOps Engineer;
- Integration Engineer.

Tech Lead назначает задачи, ревьюит каждый дифф и одобряет каждый мёрж. Architect
возвращается в работу только в двух случаях:
- решение меняет контракт между крейтами или добавляет либо убирает крейт;
- нужно архитектурное подтверждение завершённого кластера.

**Раздача задач — монополия Tech Lead.** Обходных путей нет, даже для мелочей.
Срочность выражается приоритетом в бэклоге.

### Приёмка кластера

Tech Lead помечает связанные задачи общим `cluster` **в момент планирования**. Когда
последняя задача кластера смёржена:

1. **Сначала Tester.** Он проверяет кластер и заводит баги в `tasks.jsonl` со ссылкой
   `source_task`.
2. Tech Lead назначает баги выше обычной работы. Кластер снова идёт к Tester, пока не
   станет зелёным.
3. **Последним — Architect.** Он подтверждает, что реализация соответствует архитектуре.

Для кластеров с балансовым эффектом (рост, спрос, экономика, трафик) Tech Lead между
шагами 2 и 3 просит Architect отправить Balance Analyst на headless-прогон.

### Мёрж

Ветки локальны и видны из любого worktree. Ревью — это `git diff master..<branch>` из
checkout координатора. Правила:

- **Коммит до запроса ревью.** Незакоммиченная работа возвращается непрочитанной.
- **Мёржит автор, а не ревьюер.**
- **Перед мёржем — rebase на текущий `master` и зелёный прогон**
  (`cargo test --workspace`, `cargo clippy --workspace -- -D warnings`). Если rebase
  изменил код, одобрение снимается.
- **Зелёный — это `scripts/gate.sh`, мёрж — это `scripts/ff-merge.sh`.** GitHub CI недоступен,
  поэтому гейт локальный. `gate.sh` (`set -euo pipefail`) запускает по очереди и останавливается
  на первом падении: `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
  `cargo test --workspace`, `scripts/check-sim-deps.sh`, `scripts/check-isolated-clippy.sh`; каждый
  шаг — отдельная команда с выводом в файл `$CARGO_TARGET_DIR/gate/<шаг>.log` (никаких пайпов
  после cargo: `| tail` прячет код выхода), в конце ровно одна строка `PASS: N tests` (N — сумма
  по всем `test result:`) или `FAIL: <шаг>` и код 0/1. `ff-merge.sh <ветка>` (запускается из
  worktree с этой веткой) отказывает с кодом 1, если checkout координатора (`$CITYPLANNER_COORD`,
  по умолчанию `/Users/Vladyslav_Borsh/Documents/cityplanner`) не на `master` или имеет
  незакоммиченные изменения (до запуска гейта), если ветка не содержит его `master` («rebase
  first») или в worktree есть незакоммиченное либо неотслеживаемое (не игнорируемое) — `gate.sh` тоже падает с `FAIL: untracked`; затем гоняет `gate.sh` и только при `PASS` делает
  `git -C $CITYPLANNER_COORD merge --ff-only <ветка>`. Мёржить вручную в обход скрипта нельзя.
- **Красный `master` важнее любой задачи.** Чинит тот, кто мёржил последним.
- **Не больше двух отклонений** одной задачи. Третьего раунда нет: Tech Lead возвращает
  задачу Architect или делит её сам.
- После мёржа ветка удаляется, worktree остаётся.

## Общение с пользователем

Всё, что пользователь читает напрямую (сводки, отчёты, презентации), пишется простым
языком на русском. Термин, без которого не обойтись (percentile, A*, LOD), объясняется
одной фразой при первом упоминании. Цифры и оговорки остаются такими же строгими, как в
технических документах.

## Бэклог задач

Очередь поставки — один файл, **`tasks.jsonl` в корне**: один JSON-объект на строку,
одна задача на строку.

**Два автора, разделённые по полям, а не по строкам:**
- Architect владеет полями `title`, `description` и `depends_on`;
- Tech Lead — полями `priority`, `assignee`, `status`, `branch`, `cluster` и `rejections`;
- Tester пишет только целые новые строки багов (`status: "new"`, `assignee: null`).

| Поле | Владелец | Смысл |
|---|---|---|
| `id` | создатель | `T-NNN` для задач, `BUG-NNN` для багов, `E-NNN` для эпиков вех. Не переиспользуется |
| `title` | Architect | Одна строка в повелительном наклонении |
| `description` | Architect | Что сделать и **«Done when: …»** — измеримый критерий готовности. Для бага — шаги воспроизведения (сид, сейв, команды) |
| `depends_on` | Architect | id задач, которые должны быть `merged` до старта. `[]`, если таких нет |
| `cluster` | Tech Lead | Общий тег задач, которые проверяются вместе. Ставится при планировании |
| `priority` | Tech Lead | `P0` (красный master или блокирующий баг), `P1`, `P2` |
| `assignee` | Tech Lead | `dev-1` … `dev-3`, `tech-artist`, `tester`, `integration`, `devops` или `null` |
| `status` | Tech Lead | `new` → `assigned` → `in_review` → `approved` → `merged`; также `blocked`; `epic` — для записей-эпиков вех M2–M6 |
| `branch` | Tech Lead | Ветка исполнителя |
| `rejections` | Tech Lead | Сколько раз задачу отклоняли на ревью. При `2` третьего раунда нет |
| `source_task` | Tester | Только у багов: задача, мёрж которой внёс баг |
| `created_by`, `created_at` | создатель | Роль и дата в ISO-формате |

Пример:

```json
{"id":"T-012","title":"Build the lane graph from road segments","description":"Generate per-segment lanes and junction connector lanes from cp_net nodes/segments using road definitions from cp_content. Done when: a headless test builds a 4-way junction and asserts lane count, connectivity and turn restrictions; graph rebuild after deleting a segment is covered.","depends_on":["T-010","T-011"],"cluster":"m1-roads","priority":"P1","assignee":null,"status":"new","branch":null,"rejections":0,"created_by":"architect","created_at":"2026-10-09"}
```

## Журналы

Два журнала в корне, в которые записи только добавляются. Пропустить запись в них —
дыра в процессе, а не экономия времени.

- **`IDEAS-BACKLOG.md`** — каждая идея фичи или механики, записанная **до** того, как
  она уходит Researcher или в дизайн. Поля записи: Статус, Идея, контекст (веха, затронутые
  крейты), открытые вопросы.
- **`RESEARCH-LOG.md`** — нумерованная «Запись N» на каждый законченный проход Researcher
  или Balance Analyst, **при любом исходе**. Поля: Дата, Статус, **1. Идея**,
  **2. Исследование** (кто, метод, ссылка на отчёт), **3. Результат**. Старые записи не
  переписываются.

## База знаний

Устойчивые понятия домена лежат в `knowledge/*.md`, по одному файлу на область. Примеры:
- как в CS1 считаются спрос, стоимость земли и повышение уровня;
- как устроены приоритеты на перекрёстках;
- как работают ёмкость сети и покрытие сервисов.

Файлы обновляются на месте. Это справочник, а не журнал: в нём текущее лучшее понимание и
ссылки на исследования, которые его установили. Термины, используемые в коде, сводятся в
`architecture/glossary.md`.
