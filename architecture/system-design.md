# Cityplanner — системный дизайн

Статус: v1, 2026-10-09, architect. Покрывает вехи M0–M6. M0–M1 описаны детально, M2–M6 — на уровне эпиков.
Термины даны по `architecture/glossary.md`. Задачи — в `tasks.jsonl`.

## 0. Принципы

1. **Симуляция — это продукт, рендер — её зритель.** Вся игровая логика живёт в sim-крейтах без зависимостей от рендера и оконной системы. Симуляция запускается в тестах и бенчах без окна.
2. **Детерминизм.** Одинаковые сейв, сид и лог команд на том же бинарнике и той же платформе дают одинаковое состояние, тик в тик. Это сразу даёт воспроизводимые баги, сейвы-фикстуры и регрессионные бенчи. Кроссплатформенный lockstep не обещаем: f32 может отличаться на разных CPU.
3. **Ввод — только через команды.** UI и инструменты не пишут в состояние симуляции, они отправляют `SimCommand`. Правила валидации — чистые функции в sim-крейтах, превью инструментов вызывает те же функции.
4. **Данные, а не код.** Типы дорог, зданий, сервисов и транспорта задаются RON-определениями в `assets/content/`.
5. **Население статистическое, агенты — выборка.** У каждого гражданина есть запись. Физический агент (пешеход или машина) живёт только во время поездки и берётся из ограниченного пула.
6. **Масштаб CS1 — это требование.** Решения, которые не тянут 100k жителей при 60 FPS и скорости ×3, отклоняются на дизайне, а не после.

## 2. Тик, время и исполнение

- **Отдельный мир.** Симуляция живёт в собственном `World` с собственным `Schedule` внутри ресурса `SimRunner` (`cp_sim`). Это не `FixedUpdate` клиентского приложения, поэтому headless-запуск и клиент используют один и тот же код.
- **Частота.** 1 тик = 50 мс игрового времени. При скорости ×1 это 20 тиков в секунду, при ×2 и ×3 — 40 и 60. Клиент в `PreUpdate` выполняет столько тиков, сколько накопилось, но не больше 4 за кадр; при отставании игровое время замедляется.
- **Игровое время.** 1 игровой день = 4096 тиков (≈3,4 мин при ×1), неделя = 7 дней. Бюджет списывается раз в неделю. День и ночь влияют на распорядок граждан и на освещение.
- **Бакеты.** Медленные системы обрабатывают долю объектов за тик: здания — 1/64 за тик, граждане — 1/256, блоки зонирования — 1/32. Номер бакета = `id.index % N`. Так нагрузка ровная, как в CS1.
- **Фазы расписания** выполняются строго по порядку (`SystemSet`, `.chain()`):
  1. `Commands` — применение команд, запланированных на этот тик.
  2. `Network` — обновление графа и пересчёт перекрёстков для «грязных» узлов.
  3. `Agents` — движение машин и пешеходов, перекрёстки.
  4. `Paths` — выдача готовых путей.
  5. `Citizens`.
  6. `Buildings`.
  7. `Utilities`.
  8. `Economy`.
  9. `Services`.
  10. `Stats` — счётчики, загрузка сегментов, чексумма.
- **Детерминизм под параллелизмом.**
  - `par_iter` можно использовать только по схеме «читать прошлый тик, писать свою запись».
  - Свёртки по общим аккумуляторам идут в отсортированном порядке.
  - Никаких `HashMap` или `HashSet` с итерацией: только `BTreeMap`, `IndexMap` с детерминированной вставкой или арены.
  - Никаких `Instant` и `SystemTime`.
  - Один `SimRng` (ChaCha8), производные потоки создаются через `rng.fork(stream_id)`.
- **Поиск пути вне тика.** Запрос, поданный в тик `t`, выполняется пулом потоков, а результат применяется ровно в тик `t + 8`. Если поиск не успел, фаза `Paths` ждёт его. Так время готовности результата не зависит от загрузки машины.
- **Чексумма.** Ресурс `SimChecksum` каждые 256 тиков считает FNV-хеш по аренам. Тест детерминизма: два прогона → одинаковые чексуммы.

## 3. Хранение состояния

Основные доменные данные лежат в **аренах**, а не в ECS-сущностях: `Arena<T>` — плотный `Vec<T>` с поколениями, а `Id<T>` — пара `{index: u32, gen: u32}`.

Почему арены:
- id стабильны между сейвами;
- данные компактные, удобно обходить кэш-дружелюбно и по бакетам;
- это проще, чем стабилизировать `Entity`.

ECS используется для расписания и ресурсов, а на стороне клиента — для отражения в рендере.

**Кто владеет id.** `Id<T>` типизирован элементом арены, поэтому id живёт в крейте, который владеет ареной `Arena<T>`: `cp_net` — `NodeId = Id<Node>`, `SegmentId = Id<Segment>`, `LaneId = Id<Lane>`; `cp_zone` — `ZoneBlockId`; `cp_building` — `BuildingId`; `cp_citizen` — `CitizenId`, `HouseholdId`; `cp_traffic` — `VehicleId`, `PedestrianId`; `cp_terrain` — `TileId` (не арена: индекс 0–24 в `TileOwnership`). Id определений контента (`RoadDefId`, `BuildingDefId`, …) — в `cp_content`. `cp_core` не заводит маркерных типов и псевдонимов для чужих арен: крейт, который не может назвать `Id<Segment>`, не должен и хранить его.

| Арена | Ёмкость (десктоп) | Ёмкость (WASM) |
|---|---|---|
| `Node` | 32 768 | 8 192 |
| `Segment` | 36 864 | 9 216 |
| `Lane` | 262 144 | 65 536 |
| `Building` | 49 152 | 12 288 |
| `Citizen` | 1 048 576 | 131 072 |
| `Household` | 262 144 | 32 768 |
| `Vehicle` (агенты) | 16 384 | 2 048 |
| `Pedestrian` (агенты) | 65 536 | 4 096 |
| `ZoneBlock` | 49 152 | 12 288 |

Лимиты лежат в `SimLimits` и задаются при старте. Если пул агентов полон, поездка проходит **абстрактно**: гражданин «прибывает» через время, равное стоимости пути, но без физического агента. Такие поездки учитываются в статистике.

## 4. Команды

Команда — единственный способ изменить состояние симуляции снаружи. Типы командного слоя лежат на трёх уровнях, чтобы не было цикла «`cp_core` называет типы крейтов, которые зависят от `cp_core`»:

1. **`cp_core` — обобщённая шина, без доменных типов.**
   - `CommandId(u64)` — порядковый номер, выдаётся очередью.
   - `CommandQueue<C>` — команды с тиком исполнения; `push(cmd, tick) -> CommandId`, `drain_due(tick)` отдаёт команды в порядке «тик, затем номер».
   - `CommandLog<C>` — применённые команды `(tick, CommandId, C)` в порядке применения; serde.
   - `CommandOutcome { id: CommandId, result: Result<Cost, CommandError> }` — событие.
   - `CommandError` — `InsufficientFunds { needed, available }`, `TileNotOwned`, `Rejected { domain: &'static str, reason: String }` (домен заворачивает свою ошибку валидации в `Rejected`; типизированные ошибки для превью инструменты берут напрямую из чистых функций доменов, не из исхода команды).
   - `SimSpeed { Pause, X1, X2, X3 }` — в `cp_core::time`.
   `C` ограничен `Clone + Serialize + DeserializeOwned`. Тесты шины используют собственный тестовый enum.

2. **Доменные крейты — свои команды и свои обработчики.** Каждый крейт, принимающий ввод игрока, объявляет `pub enum <Domain>Command` из типов, которыми он уже владеет, и чистую точку применения `pub fn apply(world: &mut World, cmd: &<Domain>Command) -> Result<Cost, <Domain>Error>`. Вариант добавляет задача домена, которая реализует его обработчик. Состав M1:

   | Крейт | Enum | Варианты M1 | Типы в полях (владелец) |
   |---|---|---|---|
   | `cp_net` | `NetCommand` | `BuildRoad { road, path, elevation }`, `UpgradeSegment { seg, road }`, `RemoveSegment { seg }`, `ToggleTrafficLight { node }` | `RoadDefId` (`cp_content`); `RoadPath`, `ElevationMode { Ground, Elevated(f32) }`, `SegmentId`, `NodeId` (`cp_net`) |
   | `cp_zone` | `ZoneCommand` | `PaintZones { cells: Vec<ZoneCellRef>, zone }` (`ZoneType::None` — стирание) | `ZoneCellRef { block: ZoneBlockId, cell: u16 }` (`cp_zone`); `ZoneType` (`cp_content::kinds`) |
   | `cp_building` | `BuildingCommand` | `Place { def, pos: Vec2, rot: f32 }`, `Demolish { building }` | `BuildingDefId` (`cp_content`); `BuildingId` (`cp_building`) |
   | `cp_utility` | `UtilityCommand` | `BuildLink { kind, path: Vec<Vec2> }`, `RemoveLink { link }` | `UtilityKind` (`cp_content::kinds`); `UtilityLinkId` (`cp_utility`) |
   | `cp_economy` | `EconomyCommand` | `SetTaxRate { zone, percent: u8 }`, `SetBudget { service, percent: u8 }` | `ZoneType`, `ServiceKind` (`cp_content::kinds`) |
   | `cp_terrain` | `TerrainCommand` | M2: `BuyTile { tile }` | `TileId` (`cp_terrain`) |

   Бульдозер в §4 v1 был одной командой `Bulldoze { target }` с целью из трёх крейтов; такой enum нельзя положить ни в один домен. Поэтому бульдозер — это три команды (`RemoveSegment`, `Demolish`, `RemoveLink`), а инструмент бульдозера в `cp_tools` выбирает нужную по тому, что под курсором. Отдельного `BulldozeTarget` нет.

3. **`cp_sim` — сумма и диспетчер.**

```rust
// cp_sim::command
pub enum SimCommand {
    SetSpeed { speed: SimSpeed },          // исполняет сам SimRunner, в лог пишется как любая команда
    Net(NetCommand),
    Zone(ZoneCommand),
    Building(BuildingCommand),
    Utility(UtilityCommand),
    Economy(EconomyCommand),
    Terrain(TerrainCommand),               // M2
    // M3+: Transit(TransitCommand), M4+: District(DistrictCommand), ...
}
```

   Ресурсы симуляции — `CommandQueue<SimCommand>` и `CommandLog<SimCommand>`. Диспетчер — одна эксклюзивная система в фазе `Commands`: `drain_due(tick)`, для каждой команды `match` на вариант → `apply` домена, затем списание стоимости (после задачи бюджета), запись в лог и `CommandOutcome`. `match` без `_` — компилятор не даст забыть новый вариант. «Реестра обработчиков» как структуры данных нет: реестр — это этот `match`. Домены не видят `SimCommand`; headless-тест домена кладёт `NetCommand` в `CommandQueue<NetCommand>` или зовёт `apply` напрямую.

**Правила.**
- Клиент (`cp_tools`, `cp_ui`) отправляет `SimCommand` на текущий тик + 1. Внутри тика порядок — порядок `CommandId`.
- В фазе `Commands` команда проходит валидацию той же чистой функцией, что используется в превью (`validate_road_path` и т. п.).
- Лог применённых команд сохраняется вместе с сейвом; реплей = исходный сейв + лог (`cp_save`, §12).
- **Стабильность сейвов.** `SimCommand` и доменные enum сериализуются `postcard` по номеру варианта. Новые варианты только добавляются в конец, существующие не переставляются и не удаляются; изменение полей варианта или удаление — это новая версия формата сейва и миграция (§12). Словарные enum в `cp_content::kinds` — `#[repr(u8)]`, те же правила.
- Общие перечисления, которые нужны и контенту, и командам, живут в `cp_content::kinds`, а не в `cp_core` и не в домене: `ZoneType` нужен `BuildingDef.zone`, `cp_zone` и `cp_economy`; `ServiceKind` — `ServiceDef` и бюджету; `UtilityKind` — потреблению в `BuildingDef` и `cp_utility`. Все домены достигают `cp_content` по графу §1.

## 5. Рельеф и карта

- **Размер.** Карта — 5×5 тайлов по 2048 м, всего 10 240 м. Стартовый тайл в центре.
- **Карта на диске** — каталог `assets/maps/<name>/`:
  - `map.ron`: имя, уровень моря, стартовый тайл, точки внешних связей;
  - `height.png`: 16-бит, 1025×1025, шаг 10 м, высота 0–1024 м;
  - `water.png`: маска рек и озёр поверх уровня моря;
  - `resources.png` (M5): руда, нефть, плодородие, лес.
- **Вода статична.** Поверхность = max(уровень моря, маска). Насосы ставятся только на воду глубже 2 м.
- **API.** `Terrain::height(p)` — билинейная интерполяция, `Terrain::normal(p)`, `Terrain::is_water(p)`.
- **Постройки и рельеф.** Дороги и здания не меняют рельеф в M1. Насыпи только визуальные (юбки мешей). Терраформинг — вне рамок.
- **Тайлы.** `TileOwnership` — 25 флагов. Постройка разрешена только на купленных тайлах. Стартовый набор выводится из `MapMeta.start_tile`, а не захардкожен: в M1 открыт стартовый тайл и 8 соседей (обрезка по краю карты), в M2 — только стартовый тайл, следующие покупаются за деньги по вехам. `SimRunner::set_terrain` задаёт `TileOwnership` из карты, если он ещё не задан; загрузка сейва перезаписывает его после этого.
- **Рельеф — состояние симуляции, но не часть сейва.** `Terrain` неизменяем на протяжении игры (терраформинга нет), поэтому в мире симуляции он лежит как `SimTerrain(Arc<Terrain>)`, а в сейве хранится только `map_id` и `map_hash` (§12). Загрузчик сейва сначала находит карту по `map_id` и вызывает `set_terrain`, потом восстанавливает `SaveData`. В чексумму рельеф не входит.

## 6. Дорожная сеть (`cp_net`)

### 6.1 Данные

- **`Node`**: `pos: Vec3`, `segments: SmallVec<[SegmentId; 8]>` (максимум 8), `kind: Junction|End|Middle|Outside`, `control: JunctionControl`, `elevation`.
- **`Segment`**: `start/end: NodeId`, `curve: CubicBezier3` (контрольные точки по направлениям касательных), `road: RoadDefId`, `elevation: Ground|Elevated|Bridge|Tunnel`, `lanes: SmallVec<[LaneId; 8]>`, `length`, `zone_blocks: [Option<ZoneBlockId>; 2]`.
- **`Lane`**: `segment`, `index`, `kind: Car|Pedestrian|Bike|Tram|Bus`, `dir: Forward|Backward`, `offset: f32`, `speed_limit`, `curve` (сдвиг кривой сегмента), `occupancy` (список машин, отсортированный по `s`).
- **`LaneConnection`**: связь `from_lane → to_lane` через узел, со своей кривой Безье и списком конфликтующих соединений (заполняется при пересчёте узла).
- **`RoadDef`** (RON):
  - ширина и полосы (тип, направление, смещение);
  - скорость, стоимость за метр, содержание за метр в неделю;
  - `allows_zoning`, ранг для приоритета;
  - варианты эстакады и моста;
  - id мешей и материалов.

### 6.2 Типы дорог в M1

| Тип | Полосы | Скорость | Зонирование |
|---|---|---|---|
| Двухполосная улица (`basic_2l`) | 2 + 2 тротуара | 40 км/ч | да |
| Четырёхполосная (`medium_4l`) | 4 + 2 тротуара | 50 км/ч | да |
| Шестиполосный проспект (`large_6l`) | 6 + 2 тротуара + разделитель | 60 км/ч | да |
| Одностороннее шоссе (`highway_1w_3l`) | 3 | 100 км/ч | нет; без перекрёстков в уровне, только развязки из сегментов |

Плюс версии эстакад и мостов. Односторонние улицы и тоннели — M3.

### 6.3 Постройка

- **Режимы инструмента:** прямой, кривой (3 клика), свободный.
- **Привязки** (по приоритету): к существующему узлу (до 12 м), к сегменту с его разрезанием, по углу (шаг 15°) относительно соседей, к сетке зон.
- **Ограничения:**
  - длина сегмента 8–96 м, длинный путь режется на сегменты;
  - угол между сегментами в узле ≥ 30°;
  - уклон ≤ 12% для обычных дорог и ≤ 6% для шоссе;
  - не пересекать воду без моста, не пересекать здания (их сносит с подтверждением);
  - не больше 8 сегментов в узле;
  - пересечение в уровне создаёт узел, пересечение с эстакадой — нет.
- **Эстакады и мосты.** Режим высоты `ElevationMode`: `Ground | Elevated(h)`; над водой автоматически ставится мост. Опоры — каждые 48 м.
- **Апгрейд сегмента** сохраняет узлы и пересоздаёт полосы. Зонные блоки остаются, если у нового типа `allows_zoning`.

### 6.4 Геометрия перекрёстков и связи полос

- При изменении узла он помечается «грязным» и пересчитывается в фазе `Network`:
  - сегменты сортируются по углу;
  - отступ от центра узла = функция ширин соседних сегментов и угла между ними;
  - укороченные кривые сегментов + полигон перекрёстка уходят в рендер через `SimView`.
- **Связи полос.** Для каждой входящей автомобильной полосы определяется разрешённый набор выходов:
  - крайняя правая полоса — направо и прямо;
  - крайняя левая — налево и прямо;
  - средние — прямо;
  - если какое-то направление осталось без полос, его берёт ближайшая полоса.
- **Пешеходы.** Тротуары соединяются по углам перекрёстка. Пешеходные переходы — через каждый въезд.
- **Конфликты.** Пары `LaneConnection`, чьи кривые пересекаются, плюс пары, сливающиеся в одну выходную полосу.

### 6.5 Управление перекрёстком

- **Приоритет** по умолчанию: главная дорога — это пара сегментов с наибольшим рангом, остальные уступают.
- **Светофор** ставится автоматически, если сходятся ≥ 3 сегмента и хотя бы у двух ≥ 4 полос. Его можно переключать командой.
- **Фазы светофора** — группы непересекающихся направлений по 20 с игрового времени, жёлтый 3 с. Пешеходы получают свою фазу в группе прямого движения.

## 7. Зонирование (`cp_zone`)

- **Блоки.** Каждая сторона зонируемого сегмента порождает `ZoneBlock`: сетку ячеек 8×8 м шириной `floor(len/8)` и глубиной 4, вдоль касательной сегмента. Для кривых используется кусочное приближение: колонка ячеек ориентирована по касательной в своей точке.
- **Пересечения.** Ячейки, перекрытые другим блоком, дорогой или зданием, становятся невалидными. При конфликте блоков побеждает более старый, как в CS1.
- **Типы зон:** `ResLow`, `ResHigh`, `ComLow`, `ComHigh`, `Industrial`, `Office`. Ещё `None`. Значения для M5 и M6 резервируются отдельно, через районы.
- **Инструменты:** заливка блока, кисть (малая и большая), прямоугольник, ластик. Команда `PaintZones` — список ячеек.
- **Лоты.** Лот — прямоугольник 1–4 × 1–4 ячеек, примыкающий к дороге (глубина считается от дороги). Лоты подбираются при спавне здания.

## 8. Здания (`cp_building`)

- **`BuildingDef`** (RON):
  - зона, уровень, размер лота;
  - домохозяйства или рабочие места по уровням образования;
  - потребление: вода, электричество, канализация, позже мусор;
  - налоговая база;
  - процедурный стиль: высота в этажах, тип крыши, палитра.
- **`Building`**:
  - `def`, `lot`, `level`;
  - `state: UnderConstruction|Active|Abandoned|Burned`;
  - `flags` (нет воды, нет электричества, нет работников, нет клиентов…);
  - `level_progress`, ссылки на жителей и работников.
- **Спавн.** Раз в бакет: если спрос по типу > 0 и есть валидные ячейки этой зоны, выбирается лот (детерминированно через `SimRng`) и подходящий `BuildingDef` уровня 1. Стройка длится 1 игровой день.
- **Уровни:**
  - жилые 1–5, порог — стоимость земли и покрытие сервисами (в M1 — только вода и электричество);
  - коммерция 1–3 по стоимости земли;
  - индустрия и офисы 1–3 по образованию работников.
  - Повышение уровня пересобирает здание в лоте того же размера.
- **Заброшенность.** Счётчик проблем: нет воды, нет электричества, нет работников, нет клиентов, нет товаров. Через 7 игровых дней с активным флагом здание становится заброшенным. Ещё через 7 дней оно сносится, ячейки освобождаются.
- **Сервисные здания** (насос, ЛЭП-станция, позже школы) ставятся командой `PlaceBuilding`. Они должны примыкать к дороге.

## 9. Граждане и поездки (`cp_citizen`, `cp_traffic`)

### 9.1 Граждане

- **`Citizen`**:
  - `age` (дни);
  - `education 0..=3`;
  - `household`, `home: Option<BuildingId>`, `work: Option<BuildingId>`, `school` (M2);
  - `location: Home|Work|Shop|Moving|Outside`;
  - `wellbeing`, `health` (M2);
  - `has_car`.
- **`Household`**: до 5 человек, дом, богатство.
- **Въезд.** При положительном жилом спросе и свободных квартирах домохозяйство «приезжает» через ближайшую внешнюю связь. В M1 это телепорт с задержкой, в M3 — физически.
- **Работа.** Свободные рабочие места распределяются среди безработных взрослых. Приоритет — соответствие образования, затем расстояние.
- **Выезд.** Долгая безработица или заброшенный дом → домохозяйство покидает город.
- **Взросление и смерть.** В M1 только возраст и образование при въезде. Школа, рождения и смерти — M2.

### 9.2 Распорядок

Каждый гражданин в своём бакете (1/256 за тик, то есть ≈ 16 раз в день) решает, что делать дальше:
- **Работа:** взрослые работающие едут на работу в рабочее время (смены по типу места).
- **Покупки:** с вероятностью от потребности в товарах — в коммерцию.
- **Досуг:** M6.
- **Домой:** вечером.

Решение создаёт `Trip { citizen, from, to, purpose, mode }`.

**Выбор режима** (M1):
- пешком, если путь по прямой < 1 км;
- на машине, если `has_car`;
- иначе пешком.
- В M3 добавляется общественный транспорт: режим выбирается по стоимости пути.

### 9.3 Поиск пути

- **Граф** = полосы + `LaneConnection`, отдельные подграфы машин и пешеходов. Здания подключены к сегментам через «точки доступа» (`segment`, `s`, `side`).
- **Алгоритм** — A* с эвристикой `dist / max_speed`.
- **Стоимость ребра** = `length / speed × (1 + k × congestion)` плюс штраф за повороты: налево +4 с, разворот +15 с. `congestion` — сглаженная загрузка сегмента за последние ~2 игровых часа.
- **Бюджет:** пул из `num_cpus - 2` потоков и окно в 8 тиков (см. §2). На 100k жителей ожидается ~1–2 тыс. запросов в игровую минуту, это укладывается.
- Иерархический поиск — оптимизация после M1, если бенч покажет нужду.
- Если путь не найден, поездка отменяется, а у здания-источника растёт флаг «нет доступа».

### 9.4 Агенты и движение

- **Машина** (`Vehicle`): `lane`, `s`, `speed`, `path` (список `LaneConnection`), `stuck_timer`, `kind`, `owner/trip`.
- **Пешеход** (`Pedestrian`): то же на пешеходных полосах; скорость 1,2–1,6 м/с.
- **Следование за лидером** (упрощённый IDM без смены полос внутри сегмента):
  - лидер — следующий по `s` в `lane.occupancy` (если его нет — первый на следующей полосе пути);
  - целевая скорость = min(лимит, скорость безопасной дистанции);
  - ускорение 2 м/с², торможение 4 м/с².
- **Выбор полосы.** На въезде в сегмент выбирается полоса, из которой разрешён следующий поворот; при равенстве — та, где меньше машин. Так появляются заторы на «нужной полосе», как в CS1.
- **Перекрёсток.** Перед узлом машина проверяет:
  - светофор: зелёный;
  - приоритет: в зоне 30 м на конфликтующих соединениях нет машин с приоритетом;
  - на целевой полосе есть место.
  - Иначе стоп. Соединение «занято», пока машина его не покинет.
- **Застрявшие машины.** `stuck_timer` > 3 игровых минут без движения → машина исчезает, поездка завершается абстрактно, растёт счётчик `despawned_stuck`. Порог задаётся настройкой.
- **Параллелизм.** Полосы обновляются параллельно: позиции читаются из прошлого тика, новые пишутся в буфер. Перемещения между полосами применяются в отсортированном порядке после параллельного шага.
- **Загрузка сегмента** = суммарная длина машин / (длина × число полос). EMA по 2 часам — для поиска пути, мгновенное значение — для оверлея.

## 10. Утилиты (`cp_utility`)

- **Вода.** Насос ставится на воду, производит м³/неделю. Трубы — отдельная сеть из узлов и сегментов на тех же примитивах, что `cp_net`, но без полос. Здание снабжается, если его лот в пределах 40 м от трубы, связной с насосом.
- **Канализация.** Сток у воды, ёмкость по отведению. Покрытие — по той же сети труб, как в CS1.
- **Электричество.** Станции: угольная и ветряк в M1. ЛЭП — сеть. Каждое снабжаемое здание передаёт ток зданиям в радиусе 30 м, как в CS1.
- **Распределение ёмкости.** Раз в 64 тика BFS от источников по связной компоненте, по возрастанию `BuildingId`. Каждое здание вычитает своё потребление из остатка; когда остаток кончился, оставшиеся здания получают флаг «нет …». Порядок детерминирован.
- **Оверлеи:** покрытие сетью и снабжение зданий.

## 11. Экономика (`cp_economy`)

- **Налоги.** Ставка 1–29% по каждой зоне, по умолчанию 9%. Доход здания в неделю = `def.tax_base × level_factor × rate × occupancy`.
- **Расходы:** содержание дорог (за метр по `RoadDef`), сервисных и утилитных зданий, умноженное на процент бюджета сервиса (50–150%).
- **Стартовые деньги:** 70 000. Минус разрешён до −20 000, дальше постройка запрещена.
- **Деньги в симуляции — целые центы.** `cp_core::Cost(i64)` и казна — i64 в центах; никакой float-арифметики над балансом. В RON деньги пишутся человеком в единицах валюты как `f32` (`cost_per_m: 12.5`); конвертация — `Cost::from_units(f32)`: умножить на 100 и округлить half-away-from-zero. Правило одного округления: произведение «ставка × длина/количество/процент» считается в `f64` и округляется **один раз** на транзакцию (`Cost::scaled(units: f32, factor: f64)`), а не суммируется из заранее округлённых частей. Недельное содержание — сумма i64 по сегментам и зданиям в порядке id (целочисленное сложение не зависит от порядка, но порядок фиксируем ради логов). Превью инструмента и команда используют одну и ту же функцию стоимости, поэтому их числа совпадают по построению.
- **Спрос RCIO** (стартовые формулы; калибрует balance-analyst):
  - `R = clamp(free_jobs_weighted − unemployed + base_attraction, −100, 100)`;
  - `C = clamp(resident_goods_need − commercial_capacity, …)`;
  - `I = clamp(commercial_goods_need − industrial_output + workforce_available, …)`;
  - `O = clamp(educated_workforce_available − office_jobs, …)`.
  - Значение сглаживается EMA. Обрабатываются 1/64 бакета за тик.
- **Стоимость земли** — сетка 64×64 м по всей карте:
  - + доступ к дорогам, + сервисы (M2), + парки (M6);
  - − загрязнение почвы, − шум;
  - пересчёт раз в 256 тиков.
- **Загрязнение и шум** — сетки 64 м:
  - индустрия даёт загрязнение почвы в радиусе 150 м;
  - дороги дают шум пропорционально трафику;
  - жилые здания в загрязнении получают штраф к уровню (здоровье — M2).
- **Вехи** (M2): пороги населения открывают здания, политики и тайлы. В M1 всё открыто.

## 12. Сейвы (`cp_save`)

- **Формат.** Заголовок (`magic "CPSV"`, `format_version: u32`, `content_hash: u64`, `map_id`, `map_hash: u64`, `tick`, `crc: u32`), затем `postcard`-сериализация `SaveData` (все арены, `SimRng`, `SimSpeed`, очередь и лог команд, `TileOwnership`, статистика), сжатая `zstd`. **CRC-32 считается по всему файлу, кроме самого поля `crc`:** заголовок от `magic` до `tick` и сжатое тело. Искажённый байт где угодно — ошибка загрузки, а не тихо другая карта или ложное предупреждение о контенте. (v2 покрывает CRC только тело; переход — задача T-052.)
- **Идентичность контента и карты.** `content_hash` — FNV-1a по `postcard`-кодировке каждого определения в порядке `(kind, id)`; зависит только от наших типов и правила «варианты только добавляются», а не от текстового формата сторонней библиотеки. `map_hash` — FNV-1a по `MapMeta` и сэмплам высоты и воды, считается в `cp_terrain` при загрузке карты. Несовпадение любого из них при загрузке — предупреждение, не ошибка.
- **Миграции.** Цепочка `migrate_vN_to_vN1`. Старые сейвы-фикстуры лежат в `fixtures/saves/` и обязаны загружаться в CI.
- **Несовпадение контента.** Если `content_hash` не совпал, сейв всё равно грузится, но показывается предупреждение. Неизвестные def-id заменяются заглушкой и попадают в лог.
- **Тест круга:** save → load → save даёт байт-в-байт одинаковые файлы. Тест «load + N тиков» сверяет чексумму с эталоном.

## 13. Клиент: рендер, инструменты, UI

### 13.1 Связка с симуляцией

`SimView` — read-only снапшот после каждого тика:
- позиции агентов (текущий и прошлый тик — для интерполяции);
- «грязные» сегменты, узлы, здания и блоки, чтобы пересобрать меши только для них;
- значения оверлеев;
- статистика.

Рендер не читает арены напрямую.

### 13.2 Камера

- **Управление (RTS-орбита):**
  - панорама: WASD, край экрана, средняя кнопка;
  - вращение: Q/E или правая кнопка;
  - наклон: 15–89°;
  - зум колесом к курсору.
- **Ограничения:** высота от 20 м над рельефом до 4000 м; рамка — купленные тайлы + 1 км.
- Сглаживание через инерцию.

### 13.3 Меши и LOD

| Объект | Как строится | LOD |
|---|---|---|
| Рельеф | Чанки 64×64 ячеек, нормали из heightmap, текстура по высоте и уклону | 3 уровня по дистанции |
| Вода | Плоскость на уровне моря + меш рек по маске | — |
| Дороги | Экструзия профиля `RoadDef` вдоль кривой сегмента (шаг 4 м). Перекрёсток — триангуляция полигона из `SimView`. Разметка — текстурой | Дальние сегменты без разметки |
| Здания | Процедурно из `BuildingDef`: коробка с этажами, крыша, атлас окон по зоне и уровню. Батч по чанку 256 м | Дальше 1,5 км — без деталей |
| Деревья, пропсы | CC0, инстансинг | Импосторы дальше 800 м |
| Машины | CC0 low-poly, GPU-инстансинг по типу | Видны при высоте камеры < 800 м |
| Пешеходы | CC0 low-poly, инстансинг, без скелетной анимации в M1 (покачивание вершинным шейдером) | Видны < 250 м |

Симуляция работает всегда, независимо от зума. Рендер отбирает агентов по фрустуму и порогам выше.

### 13.4 Оверлеи

Трафик (цвет дороги по загрузке), вода, электричество, зоны, стоимость земли, загрязнение. Реализованы как вариант материала с uniform-буфером значений по id.

### 13.5 Инструменты (`cp_tools`)

- Каждый инструмент — состояние + превью-«призрак» + стоимость + ошибки валидации из чистых функций `cp_net`, `cp_zone`, `cp_building`.
- По клику — `SimCommand`.
- Бульдозер работает с сегментом, зданием или зоной; наведение подсвечивает цель.

### 13.6 UI (`cp_ui`, egui)

- Нижняя панель категорий: Дороги, Зоны, Вода, Электричество, Сервисы (M2), Транспорт (M3), Районы (M4)…
- Верх: деньги, население, бары спроса RCIO, дата и время, скорость, оверлеи.
- Инфопанели: здание (уровень, жители, рабочие, проблемы), гражданин, машина (маршрут), сегмент (загрузка).
- Бюджет: налоги и бюджеты сервисов.
- Сейв и загрузка, отладочное окно (тики/с, мс по системам, размер пулов, чексумма).

## 14. Производительность

| Бюджет на кадр (16,6 мс) при 100k жителей и скорости ×3 | Цель |
|---|---|
| Sim, всего, CPU (основной поток + воркеры) | ≤ 8 мс |
| — агенты (16k машин, ~20k пешеходов в пути) | ≤ 3 мс |
| — граждане, здания, экономика, утилиты (бакеты) | ≤ 1,5 мс |
| — поиск пути (фоновые потоки, не на основном) | ≤ 2 ядра |
| Подготовка рендера, CPU (экстракция, инстанс-буферы) | ≤ 3 мс |
| GPU | ≤ 10 мс на M1 или GTX 1660 при 1080p |

- **Бенч.** `apps/bench` строит город сценарием `cp_sim::scenario::grid_city(target_pop, seed)` или грузит `fixtures/saves/bench-*.sav`, гонит N тиков и печатает мс/тик по фазам в JSON.
- **CI.** Бенч на 10k жителей запускается на каждый PR, на 100k — ночью. Регрессия > 20% относительно `bench/baseline.json` помечается как ошибка. Шум раннеров учитывается медианой из 5 прогонов.

## 15. Платформы

- **Десктоп:** macOS, Windows, Linux; бэкенд рендера Vulkan, Metal или DX12 через wgpu. Целевая платформа.
- **WASM:** WebGL2 (фича Bevy `webgl2`), однопоточный. Поиск пути выполняется в фазе `Paths` синхронно. Лимиты агентов — WASM-колонка из §3. Сборка проверяется в CI. Демо обязано загрузиться и держать 30 FPS на городе в 10k жителей.

## 16. Вехи M2–M6 (эпики)

### M2 — Сервисы и прогрессия (E-002)
- `cp_service`: `ServiceDef` (радиус покрытия по дорогам, вместимость, машины). Покрытие = Дейкстра по дорогам от здания до порога стоимости. Результат пишется в сетку и в здания.
- Мусор: здания копят мусор, мусоровозы физически едут по маршруту (диспетчер выбирает ближайшие заявки), свалка или мусоросжигатель.
- Здоровье: больница и скорые, кладбище и катафалки, болезнь от загрязнения.
- Полиция: преступность растёт от отсутствия покрытия, патрули.
- Пожарные: пожар — событие со случайным шансом (ниже при покрытии), машина должна доехать, иначе здание сгорает.
- Образование: начальная школа → старшая → университет. Вместимость; ученики ездят как обычные поездки. Уровень образования граждан растёт.
- Жизненный цикл: рождения, взросление, смерть.
- Вехи населения и покупка тайлов (`BuyTile`); в M2 стартовым остаётся только центральный тайл.
- Уровни жилья начинают зависеть от сервисов.

### M3 — Общественный транспорт и внешние связи (E-003)
- `cp_transit`: `TransitLine` (упорядоченные остановки по графу, транспорт на линии, интервал).
- Режимы: автобус (по дорожным полосам), трамвай (трамвайные пути в дороге и отдельно), метро (тоннели и станции), поезд (ж/д сеть, вокзалы).
- Пересадки и выбор режима — мультимодальный A*: пешком + линии со стоимостью ожидания.
- Тоннели, односторонние дороги, развязки-шаблоны.
- Внешние связи (шоссе, ж/д): въезд и выезд граждан, туристы, импорт и экспорт товаров. Грузовики между индустрией и коммерцией становятся физическими агентами.

### M4 — Районы, политики, уникальные здания (E-004)
- `cp_district`: рисование районов кистью по сетке 32 м, имя, статистика района.
- Политики (запрет тяжёлого транспорта, высотность, налоговые льготы…) — модификаторы систем через `PolicyDef`.
- Специализации зон (туризм и досуг для коммерции, IT для офисов, «зелёное» жильё).
- Уникальные здания и монументы: условия разблокировки, бонусы к привлекательности и стоимости земли, туризм.

### M5 — Индустриальные районы (E-005)
- `cp_industry`: индустриальная зона рисуется как район по ресурсу (агро, лес, руда, нефть) из `resources.png`.
- Главное здание зоны, уровни зоны, работники.
- Цепочка: добывающие → перерабатывающие → склады → уникальные фабрики → коммерция и экспорт.
- Грузы — физические грузовики (используется грузовой трафик из M3).
- Сюда же — склады и почтовая служба.

### M6 — Парковые зоны (E-006)
- `cp_park`: парковая зона (городской парк, природный заповедник, зоопарк, парк развлечений).
- Главные ворота, здания и пропсы внутри, пешеходные дорожки (новый тип пешеходного сегмента в `cp_net`).
- Посетители (поездки досуга из §9.2), уровень парка по числу посетителей, доход за вход, влияние на стоимость земли.

## 17. Риски и как их снимаем

| Риск | Мера |
|---|---|
| Сложность геометрии перекрёстков и кривых | Отдельный кластер задач с визуальным дебаг-рендером и property-тестами (нет самопересечений, связи полос симметричны) — до зданий и трафика |
| Производительность трафика | Бенч появляется в M0, раньше трафика. Сценарий `grid_city` позволяет мерить без UI. Параллельный шаг по полосам — с первого дня |
| Нарушения детерминизма | Тест двойного прогона с чексуммой в CI с M0. Clippy-линт `disallowed_types` на `HashMap`/`HashSet` в sim-крейтах |
| Breaking changes Bevy | Версия зафиксирована. Обновление — отдельная задача devops раз в релиз Bevy, не попутно |
| Пробки, «умирающие» из-за despawn | Порог стопора настраивается, счётчик `despawned_stuck` — метрика баланса |
